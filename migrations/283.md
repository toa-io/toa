# Migrating to 1.0.0-alpha.283

Pod labels are renamed and namespaced. Every Deployment must be removed before upgrading.

A composition may run extension services in its own pod.

## Pod labels

Every label the chart sets now carries a `toa/` prefix, and membership is stated per member
rather than per kind:

| | before | after |
|---|---|---|
| composition | `toa.io/composition: <name>` | `toa/composition: <name>` |
| service deployment | `toa.io/service: extension-<g>-<n>` | `toa/service: extension-<g>-<n>` |
| a component is in this pod | `<namespace>-<name>: "1"` | `toa/component-<namespace>-<name>: "1"` |
| a service is in this pod | — | `toa/service-<g>-<n>: "1"` |

A pod holds one value per key, so `toa.io/service` could not say that a pod runs two services.
The boolean form can, and it needed the prefix: `configuration` ships the component
`configuration.values` beside the service `configuration`/`values`, and `realtime` ships
`realtime.streams` beside `realtime`/`streams` — each pair flattened to one label.

## What to do

A Deployment's `spec.selector` is immutable, so `helm upgrade` refuses the rename. Remove the
existing Deployments first; the upgrade recreates them:

```shell
$ kubectl delete deployment -l toa.io/composition -n <namespace>
$ kubectl delete deployment -l toa.io/service -n <namespace>
```

Anything of your own that selects on the old labels — a NetworkPolicy, a ServiceMonitor, a
dashboard query — is updated to the new ones.

## A composition may run services

```yaml
# context.toa.yaml

compositions:
  - name: edge
    components:
      - todos.tasks
    services:
      - exposition
```

A service is named by shortcut or package reference. One a composition lists gets no Deployment
of its own; its `Service` and its `Ingress` stay, under the same names, and select the pods of
the composition running it. `extension-exposition-gateway` resolves the same whether the gateway
is deployed on its own or inside a composition.

Listing one service in several compositions is replication: every pod running it carries the
label, one `Service` selects them all, and there is one `Ingress` regardless. A service no
composition lists is deployed as it was.

See [compositions](../documentation/compositions.md).

`--mono` is unchanged. It still takes every component and every service, including one a later
release adds, and its workload is still named `mono`.

## Ports are claimed per pod

A workload that runs services puts them in one process, so a port is claimed once within one.
Two compositions may each bind the same port, where before a port was claimed once per context.

## A composition is validated

An unknown component is refused by name, where it used to fail as
`Cannot read properties of undefined (reading 'locator')`:

```
Composition 'edge' lists an unknown component 'todos.three'.
```

An extension listed as a service that runs none is refused:

```
Composition 'edge' lists '@toa.io/extensions.telemetry', which contributes no service.
```

An unknown key in a composition is refused, where it used to be ignored. A context that
misspelled one has been deploying without it.

## Running a composition with services locally

`toa compose` takes `--service`, and reads `TOA_SERVICES` when it is not given, which is what
the deployment sets:

```shell
$ toa compose ./components/* --service exposition --service configuration
```

The list is exact — unlike `toa mono`, nothing is discovered. A service the named ones talk to
answers over the network in a deployment; in one process it is named too, or nothing answers it.
