# Migrating from 1.0.0-alpha.288

## Migrations are inherited

A prototype's migrations are applied to the collection of every component that takes it, ahead of
the component's own, and recorded as `<prototype>:<id>` in `system_migrations`. A prototype of
yours that declares migrations has to have a `name`, or the component does not load:

```
Prototype at '/app/components/base' declares migrations, so it has to be named
```

The rename of the system properties and their conversion to dates are the root prototype's
migrations, `system:0000-property-names` and `system:0001-epoch-millis`, applied to every
collection in that order. A database taken from `1.0.0-alpha.285` or earlier straight to `287` or
`288` had the conversion run before the rename and holds `CREATED` as a number. A row
`<collection>:system:0001-epoch-millis` already recorded is not applied again, so delete those
rows before deploying where that is the case, and the conversion runs at start:

```javascript
db.system_migrations.deleteMany({ _id: /:system:0001-epoch-millis$/ })
```

`migrations/0001-system-properties.yaml` in a component of yours is not needed: delete it. One
left in place is applied once and changes nothing.

A component on a storage that does not apply migrations — `@toa.io/storages.null`, one of your
own — starts with inherited migrations and is refused only for its own.

## What to do

1. Name every prototype of yours that declares migrations.
2. Delete `migrations/0001-system-properties.yaml` from every component of yours.
3. Where a database went from `285` or earlier straight to `287` or `288`, delete the recorded
   `system:0001-epoch-millis` rows, then deploy with every replica stopped.

## The deployment library is a package of its own

`toa deploy`, `toa build`, `toa push`, `toa env`, `toa export` and `toa conceal` need
`@toa.io/operations`, which `@toa.io/runtime` no longer depends on. A CLI that finds it missing
says so:

```
`toa deploy` needs @toa.io/operations, which is not installed
```

An image the runtime is built into carries no `@toa.io/operations`, so a process cannot deploy.

## The `toa` binary is `@toa.io/cli`'s

`@toa.io/runtime` declares no binary. npm links a dependency's binaries into `node_modules/.bin`,
so an application that installs the runtime has `toa` as before. A global install of the runtime
has it no longer: install locally and put `node_modules/.bin` on the `PATH`, as the runtime image
does, or link the binary.

## What an extension declares is read from `@toa.io/definitions`

`manifest`, `components`, `deployment`, `image`, `standalone`, `context` of an extension Toa ships,
`properties` of a binding and `define` of a bridge are exported from `@toa.io/definitions`, not
from the extension: `import { describe } from '@toa.io/definitions/extensions.configuration'`. An
extension of your own that exports them beside its `Factory` is read as before, and may ship a
`definition.js` to be read without loading what it runs.

## An operation is read from its source

A bridge reads the type and the scope of an operation from the module's source, not from the
loaded function. `export const transition = wrap(fn)` names its type and nothing else: declare
`scope` in the manifest for such an operation. A `.ts` that Node cannot erase is refused when it
is loaded to run rather than when it is read.

## What to do

1. Add `@toa.io/operations` to `devDependencies` where `toa deploy` runs.
2. Import what an extension declares from `@toa.io/definitions/<package>`, if you did.
3. Declare `scope` for an operation whose exported value is computed rather than written.
4. Where the runtime was installed globally for its binary, install it locally and put
   `node_modules/.bin` on the `PATH`, as the runtime image does.
