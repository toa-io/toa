# Migrating to 1.0.0-alpha.283

Pod labels are renamed and namespaced. Every Deployment must be removed before upgrading.

A composition may run extension services in its own pod.

An operation returns the errors it declares and no others, and a reply is no longer rewritten
as it is validated.

`toa types` writes an application's TypeScript types from its manifests.

## Pod labels

Every label the chart sets now carries a `toa/` prefix, and membership is stated per member
rather than per kind:

| | before | after |
|---|---|---|
| composition | `toa.io/composition: <name>` | `toa/composition: <name>` |
| service deployment | `toa.io/service: extension-<g>-<n>` | `toa/service: extension-<g>-<n>` |
| a component is in this pod | `<namespace>-<name>: "1"` | `toa/component-<namespace>-<name>: "1"` |
| a service is in this pod | — | `toa/service-<g>-<n>: "1"` |

A pod holds one value per key, so `toa.io/service` could not say that a pod runs two services.
The boolean form can, and it needed the prefix: `configuration` ships the component
`configuration.values` beside the service `configuration`/`values`, and `realtime` ships
`realtime.streams` beside `realtime`/`streams` — each pair flattened to one label.

## What to do

A Deployment's `spec.selector` is immutable, so `helm upgrade` refuses the rename. Remove the
existing Deployments first; the upgrade recreates them:

```shell
$ kubectl delete deployment -l toa.io/composition -n <namespace>
$ kubectl delete deployment -l toa.io/service -n <namespace>
```

Anything of your own that selects on the old labels — a NetworkPolicy, a ServiceMonitor, a
dashboard query — is updated to the new ones.

## A composition may run services

```yaml
# context.toa.yaml

compositions:
  - name: edge
    components:
      - todos.tasks
    services:
      - exposition
```

A service is named by shortcut or package reference. One a composition lists gets no Deployment
of its own; its `Service` and its `Ingress` stay, under the same names, and select the pods of
the composition running it. `extension-exposition-gateway` resolves the same whether the gateway
is deployed on its own or inside a composition.

Listing one service in several compositions is replication: every pod running it carries the
label, one `Service` selects them all, and there is one `Ingress` regardless. A service no
composition lists is deployed as it was.

See [compositions](../documentation/compositions.md).

`--mono` is unchanged. It still takes every component and every service, including one a later
release adds, and its workload is still named `mono`.

## Ports are claimed per pod

A workload that runs services puts them in one process, so a port is claimed once within one.
Two compositions may each bind the same port, where before a port was claimed once per context.

## A composition is validated

An unknown component is refused by name, where it used to fail as
`Cannot read properties of undefined (reading 'locator')`:

```
Composition 'edge' lists an unknown component 'todos.three'.
```

An extension listed as a service that runs none is refused:

```
Composition 'edge' lists '@toa.io/extensions.telemetry', which contributes no service.
```

An unknown key in a composition is refused, where it used to be ignored. A context that
misspelled one has been deploying without it.

## Running a composition with services locally

`toa compose` takes `--service`, and reads `TOA_SERVICES` when it is not given, which is what
the deployment sets:

```shell
$ toa compose ./components/* --service exposition --service configuration
```

The list is exact — unlike `toa mono`, nothing is discovered. A service the named ones talk to
answers over the network in a deployment; in one process it is named too, or nothing answers it.

## An operation returns the errors it declares, and no others

`errors` had no effect before this release: the reply contract was built from `error`, which no
manifest declares. Any error with a `code` was accepted, declared or not.

Where a reply is validated — `TOA_ENV=local`, as before — an error is now refused as
`ResponseContract` (211) unless the operation declares its code:

```yaml
operations:
  transit:
    errors: [EXISTS, INVALID_USERNAME]
```

An operation declaring no `errors` returns none. One that propagates an error from a call it
makes declares that error too.

## A reply is read as it is

The reply contract no longer coerces or fills in defaults. An output that fits only once
converted does not fit, and a default the schema states is not filled in:

```yaml
output:
  type: object
  properties:
    value:
      type: string
```

Returning `{ value: 1 }` was accepted on a local run, and the caller got `{ value: "1" }` —
the schema's conversion rather than what the operation returned. It is now refused.

Request and entity contracts are unchanged: an input default is declared behaviour and still
applies.

## `toa types`

An application's types are generated from what its manifests already state:

```shell
$ toa types -p ./application
```

Written are `types/` beside `context.toa.yaml` and a `types.ts` beside every component's
manifest, each with the `package.json` naming it — `@components/<directory>` for a component,
the Context's own `name` for the Context. Both are Toa's: every run rewrites them.

A component's `Context`, `Entity`, `<Operation>Input` and `<Operation>Output` come from its
manifest; `remote` covers every component of the Context, the ones its extensions contribute
included. What a manifest does not state is not generated — an operation declaring no `output`
returns `unknown`, unless it is one Toa itself provides. An alias for something a schema does
describe belongs in a file of your own:

```typescript
import type { Entity } from '@components/activities'

type Plugin = Entity['plugins'][number]
```

The types Toa ships are `@toa.io/userland/types` from here. `@toa.io/types` re-exports them and
is deprecated; `Stash` moved to `@toa.io/extensions.stash`, and `Storage` and `Logs` were
already their extensions' own.

### A configuration value may declare that it is a secret

```yaml
configuration:
  schema:
    properties:
      token: { type: string, format: secret }
```

Whether a value becomes a `Secret` is decided by the deployed value — a `$VARIABLE` reference —
which a schema cannot see. `format: secret` states it, and is what gives the generated type
`Secret` rather than `string`. It constrains no value.

## A list says once what both sides say

Merging two lists no longer repeats what they share. A prototype requiring `id` of a component
that requires it too used to produce `[id, ..., id]`, which the manifest schema then refused as
non-unique — reported against `/entity/schema/required` rather than against the declaration that
caused it:

```yaml
entity:
  schema:
    required: [id, title]   # refused before this release
```

The same held wherever a list is inherited: `bindings`, and the `errors` of an operation that
forwards to one declaring the same codes.

Lists of objects are unchanged: two that look alike are still two.
