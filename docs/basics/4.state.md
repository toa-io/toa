# State

A component's state is a collection of entity objects that only its own operations can change.
The entity schema says what a valid object looks like. This article describes what the runtime
maintains around that state: identity, validity, versions, invariants, and deletion.

## Identity and creation

Every entity object has an `id`, assigned by the runtime. An operation never generates or stores
it.

Creation is not a separate kind of operation. A transition called *without* a query has no
existing entity to retrieve, so it runs against a new one:

```javascript
// creates an order
await context.remote.orders.transit({
  input: { customer, total: 1500 }
})

// changes an existing order
await context.remote.orders.transit({
  query: { id: orderId },
  input: { total: 1200 }
})
```

The same implementation serves both calls. In the first, it receives a blank order and its
commit creates the entity; in the second, it receives the current state of the order the query
selects. A query that selects nothing is a failure of the call: the operation does not run
against an order that is not there.

A schema can state what a blank object holds before anything is written to it:

```yaml
entity:
  properties:
    customer: { type: string }
    status: { type: string, enum: [pending, approved, cancelled] }
    total: { type: integer, minimum: 0 }
  required: [customer, status, total]
  blank:
    status: pending
```

Some entities are identified by something that already exists elsewhere, such as a wallet that
belongs to a customer. An entity declared `associated` takes its identity from outside: any `id`
names one, a read of an entity never written returns its blank, and the first write creates it.

## Validity

The runtime validates state against the entity schema when it commits. A transition that leaves
an order without a customer, or with a negative total, does not commit: the invalid state never
reaches storage, whichever operation produced it.

This places the definition of valid state in one declaration instead of in every operation that
writes.

## Versions and concurrency

Each entity carries a `VERSION` that increases with every committed write. It is how the runtime
detects that state changed between an operation's Retrieve and its Commit.

Suppose two calls reduce the same order's total at the same moment. Both retrieve version 4;
one commits version 5. The other's commit no longer applies to the state it read. The runtime
does not let it overwrite the first change. What happens instead is declared by the operation:

```yaml
operations:
  reduce:
    concurrency: retry
```

With `retry`, the runtime retrieves the fresh state and runs the implementation again. The
decision is re-made against version 5, as though the calls had arrived in sequence. Without it,
the call fails and the conflict is the caller's to handle.

This is *optimistic* concurrency control: nothing is locked while an operation runs, and a
conflict costs a re-run only when one actually occurs. It is also why a transition's
implementation has to be safe to run more than once for a single call.

A caller can take part in the same check. A query may name the version the caller last saw, and
the operation then applies only if the entity is still at that version.

## Guards

A schema constrains one state. Some rules constrain a *change*: a total that may only decrease,
a status that never leaves `cancelled`. A *guard* states such an invariant once, for every
operation of the component:

```javascript
// guards/total.js
function guard (order, origin) {
  return origin === null || order.total <= origin.total
}
```

The runtime evaluates guards at commit, with the state about to be written and the state it
replaces (`origin`, or `null` for a new entity). A change that violates a guard is not
committed. The invariant holds regardless of which operation attempted the change, including
operations inherited from a prototype.

## Deciding not to commit

A transition can run, look at the current state, and conclude that there is nothing to change.
Marking the state as discarded tells the runtime to skip the commit: nothing is written, no
version is consumed, and no event is produced. The caller still receives the operation's reply.

```javascript
async function transition (input, wallet) {
  if (wallet.balance < input.amount) {
    wallet.DISCARD = true

    return { balance: wallet.balance, charged: false }
  }

  wallet.balance -= input.amount

  return { balance: wallet.balance, charged: true }
}
```

Unlike an error, this is a successful outcome with an output of its own; it differs only in
leaving the state untouched.

## Deletion

Nothing removes an entity from storage. Deletion is a state change: the entity is marked with
the time it was deleted, and from then on queries do not find it. The generic prototype's
`terminate` operation makes that change.

A deleted entity keeps its history and its identity. Other entities that referred to it do not
end up pointing at nothing, and the deletion itself is a committed change like any other: it has
a version, and it is announced by an event.
