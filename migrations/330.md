# Migrating from 1.0.0-alpha.330

## A code issued with an identity ties the username once it is confirmed

`identity.otp.issue` with `identity` no longer ties the username to the identity: the code does,
once the identity sends it back. Before, the username was tied as the code was issued, so whoever
could call `issue` could tie an address they did not hold to an identity of their choosing.

Such a code does not sign in either: `GET /identity/` with it is refused with `401`. A code for an
identity's own id, which `POST /identity/otp/:identity/` issues, signs in as before.

1. Where a code issued with `identity` is entered, send it to the identity's route with its token:

   ```http
   PUT /identity/otp/<identity>/ HTTP/1.1
   authorization: Token ...
   content-type: application/yaml

   username: bob@example.com
   code: '493817'
   ```

   It answers `204`, or `422` with `EXPIRED`, `TOO_MANY_ATTEMPTS`, or `EXISTS` for a username tied
   to another identity already.

2. Review the records of `identity_otp` that an `issue` with `identity` wrote: none of them was
   proven. Nothing tells them from the others.
