# Replies

A call ends in one of three ways: the operation answers with an output, it answers with an
error, or it fails with an exception. The first two are replies. The third is not.

## Output

What an operation's implementation returns is its output. An operation can declare the shape of
that output, as it declares its input:

```yaml
operations:
  reduce:
    type: transition
    input:
      type: object
      properties:
        amount: { type: integer, minimum: 1 }
      required: [amount]
    output:
      type: object
      properties:
        total: { type: integer }
```

Input and output schemas together form the operation's *contract*: what a caller may send and
what it can expect back. The runtime holds both sides to it.

## An error is an answer

Some outcomes are refusals the business logic expects: the order is not pending, the amount
exceeds the total, the balance is insufficient. An operation expresses such an outcome by
*returning* an error that carries a code:

```javascript
async function transition (input, order) {
  if (input.amount > order.total)
    return AMOUNT_EXCEEDS_TOTAL

  order.total -= input.amount

  return { total: order.total }
}

const AMOUNT_EXCEEDS_TOTAL = Object.assign(new Error(), { code: 'AMOUNT_EXCEEDS_TOTAL' })
```

The codes an operation may answer with are part of its contract:

```yaml
operations:
  reduce:
    errors: [AMOUNT_EXCEEDS_TOTAL]
```

A refusal is the operation working as designed. The runtime treats it as a successful exchange
whose content happens to be "no": nothing is committed, nothing is retried, and nothing is
reported as a failure. An error with a code the operation did not declare is not an answer it is
allowed to make.

## An exception is a failure

Anything *thrown* is a failure nobody chose: a defect in the code, or something the operation
depends on being unavailable. Exceptions are not declared, because they are not part of what the
operation means to say.

The runtime raises exceptions of its own for the same kind of situation: a request that does not
fit the contract, an entity that does not exist, a concurrent change the operation was not
allowed to retry.

## What a caller receives

A caller receives a reply as a value and can tell an error from an output:

```javascript
const reply = await context.remote.orders.reduce({
  query: { id: orderId },
  input: { amount: 500 }
})

if (reply instanceof Error) {
  if (reply.code === 'AMOUNT_EXCEEDS_TOTAL')
    return REFUND_REJECTED

  return reply
}
```

An error is handled where it has meaning or passed on as the caller's own answer. An exception
is not a value: it is thrown at the point of the call. An operation that does not catch it fails
in turn, and the failure reaches whoever is waiting at the start of the chain.

## Why the distinction matters

The two outcomes drive different behavior throughout the runtime, so the choice between
returning and throwing is not stylistic.

| | Error | Exception |
| --- | --- | --- |
| Meaning | An expected refusal. | An unexpected failure. |
| Expressed by | Returning a coded `Error`. | Throwing. |
| Declared | In the operation's `errors`. | Never. |
| For a caller | A value to inspect. | Thrown where the call was made. |
| Where nobody is waiting | The message is done with. | The message is tried again. |

The last row is where the difference becomes consequential. An event or a task has no caller to
receive the answer, so a refusal simply ends the work, while a failure makes the runtime try
again. A refusal expressed by throwing would be retried as though something were broken.
[Delivery](../reliability/1.delivery.md) describes that behavior, which is the runtime's
distributed exception handling.
