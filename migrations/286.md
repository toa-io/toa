# Migrating to 1.0.0-alpha.286

A component's indexes and its data changes are declared together, as migrations, and
`entity.index` and `entity.unique` are gone.

The SQL storage connector is gone.

**This release requires downtime.** It ships the system-property rename, which the release before
it cannot read, so the two must not run at once — see
[285](285.md#the-old-and-the-new-version-must-not-run-at-once).

## Indexes move into migrations

`entity.index` and `entity.unique` are no longer part of a manifest, and one that still declares
them fails validation:

```
Property index is not expected to be here
```

What they declared is now a file in the component's `migrations` directory. Write one that
reproduces the indexes the database already has, and delete the manifest block:

```yaml
# manifest.toa.yaml — before
entity:
  unique:
    authority_username: [authority, username]
  index:
    username:
      authority: asc
      username: asc
```

```yaml
# migrations/0001-indexes.yaml — after
- index:
    name: unique_authority_username
    keys: { authority: asc, username: asc }
    unique: true
- index:
    name: index_username
    keys: { authority: asc, username: asc }
```

The translation is mechanical, and it has to be exact, or the first run drops a live index and
builds it again:

- `unique: { <key>: [<fields>] }` becomes `name: unique_<key>`, `keys` with every field `asc`,
  `unique: true`, and `partial: { DELETED: null }` — see below. Where a field is not in
  `schema.required`, add `<field>: { $exists: true }` to that same `partial`.
- `index: { <key>: { <field>: <direction> } }` becomes `name: index_<key>` and the same `keys`.
  Where a field is not in `schema.required`, add `sparse: true`.

`VERSION`, `CREATED`, `UPDATED` and `DELETED` count for that rule like any other field: a
component that does not list one in `required` had a sparse index over it, and the migration says
`sparse: true` to keep it.

Written that way an ordinary index is a no-op against a database that already has it. A unique
one is rebuilt, because of the filter the next section adds. Get the rest wrong and the first run
drops a live index and builds it again, which on a large collection is a stall, not a failure.

### A unique index holds over live records only

Nothing is hard-deleted, so a tombstone under a plain unique index holds its key for good: delete
an identity and its username can never be registered again, revoke a role and it can never be
granted again. Every unique index this release ships is declared with a filter that leaves
tombstones out, and yours should be:

```yaml
- index:
    name: unique_email
    keys: { email: asc }
    unique: true
    partial: { DELETED: null }
```

Uniqueness still holds among live records; only the tombstones stop reserving keys. The index is
rebuilt on the first run, because the live one has no such filter.

### What else is rebuilt

One index gets rebuilt whatever you write: one whose keys include `_version`, `_created`,
`_updated` or `_deleted`. The live index is over a name nothing writes after the rename of this
same release, so it is dropped and built again over the new one. Three of the components shipped
here are in that position — `configuration.values`, `identity.federation` and `identity.passkeys`
— and so is any of yours that sorts or filters on one of the four.

See [Migrations](/documentation/component/declaration.md#migrations) for what a migration may say.

### An index changes by being edited

Changing an index used to require renaming it. Under its old name the change was refused by
MongoDB, the refusal was logged as a warning, and the database kept the index it had.

Now an index whose name is held by one of another shape is dropped and made again, so an index
changes by editing its declaration — in a new migration, because a migration that has run is not
run again:

```yaml
# migrations/0007-widen-the-lookup.yaml
- index:
    name: index_lookup
    keys: { component: asc, epoch: asc, CREATED: desc }
```

### Migrations are not inherited

A migration is applied to a collection and a prototype has none, so what a prototype declares
stays with it. A component that takes a prototype's schema writes its own migrations — including
the one for the system-property rename of this same release, see [285](285.md#existing-data).

### What is applied, and when

A migration is applied once for the database rather than once per replica, and never again. The
runtime keeps a `system_migrations` collection beside the component collections to record that;
dropping a row is what makes a migration run again.

A migration runs before the component serves and the other replicas wait for it, so a rollout
waits for the longest one. A replica that dies while applying a migration has it applied again
from its first step, which is why a migration must be idempotent — write an `update` filter that
excludes what it has already changed.

Nothing prunes an index any more. Before, an index the manifest did not name was dropped on every
start; now an index nobody declared is left alone, and one that is no longer wanted is dropped by
a `dropIndex` step.

### Deployment procedure

**This release is not deployed by a rolling update**, because of the system-property rename it
ships with — see [285](285.md#the-old-and-the-new-version-must-not-run-at-once). Stop every
replica of the release before it first.

That is a property of this release, not of migrations. An index migration is safe to roll out
either way; a data migration needs the release before it to still be able to read what it leaves,
and where it cannot, the deployment stops first.

1. Write `migrations/0002-indexes.yaml` for every stored component that declares `index` or
   `unique`, and remove the declarations. Write `0001-system-properties.yaml` beside it,
   see [285](285.md#existing-data).
2. Confirm the manifests still validate:

   ```shell
   toa export deployment <environment>
   ```

3. Back the database up, then stop every replica of the release before this one.
4. Deploy. Read `system_migrations` afterwards to see what was applied:

   ```
   { _id: 'identity_basic:0002-indexes', state: 'done', ... }
   ```

   A row still `running` long after a rollout is a migration whose replica died and whose lease
   has not yet been taken over; a row that is `done` needs nothing.

### Rollback

An older runtime ignores `migrations` and manages `entity.index` again — but the manifests no
longer declare any, so it would find none and drop every index the migration built. Roll the
Context back together with the runtime, or not at all.

It cannot read the records either, for the same reason the two versions must not run at once, so
a rollback is a stop, a restore of the backup taken before the upgrade, and a start — not a
redeploy of the version before this one over the database it left behind.

## The SQL storage is removed

`@toa.io/storages.sql` is no longer published, the `sql` storage shortcut is gone, and a component
that declares `storage: sql` does not resolve. It never implemented `index` or `unique` and does
not implement migrations.

There is no replacement. An application on it either pins `1.0.0-alpha.284` of the connector and
keeps a copy of its own, or moves the component to MongoDB.

The `sql` Context annotation goes with it:

```yaml
# context.toa.yaml — remove
sql: pg://host0.example.com/production
```
