# Migrating to 1.0.0-alpha.284

A component may be written in TypeScript, and is read as it is.

Two files that resolve to one module name are refused rather than ranked.

## A component may be written in TypeScript

An operation, an event, a receiver, a guard or a run command may be a `.ts`. Node erases the types
and compiles nothing else, so there is no build step, no output directory and no loader — the file
beside the manifest is the file that runs.

```javascript
// operations/create.js

export async function transition (input, object, context) {
  return { id: object.id }
}
```

```typescript
// operations/create.ts

import type { Context, CreateInput, Entity } from '../types/index.d.ts'

export async function transition (input: CreateInput, object: Entity, context: Context) {
  return { id: object.id }
}
```

The name a module exports still says what it is, and the second parameter still says the scope.

Three rules follow from Node reading the file rather than compiling it. A relative import carries
the extension of the file that exists, because nothing rewrites a specifier:

```typescript
import { credentials } from './lib/credentials.js'
```

```typescript
import { credentials } from './lib/credentials.ts'
```

A type is imported with `import type`, because an import that is not marked as one is kept and then
resolved at runtime. This is also what keeps a component's types off its runtime graph, so
`import type` from `@toa.io/*` does not break the rule that component code depends on no Toa
package:

```typescript
import { type Context } from '../types/index.d.ts'
```

```typescript
import type { Context } from '../types/index.d.ts'
```

And the syntax has to be erasable: an `enum`, a `namespace` and a parameter property emit code, so
Node refuses them, naming the file and the rule. A component that is typechecked can be told to
refuse them first, with `erasableSyntaxOnly`. The `tsconfig.json` to use is in the
[Node bridge readme](../connectors/bridges.node/readme.md).

A component written this way states `"type": "module"` in a `package.json` beside its manifest, as
any component that is a module does. `toa build` restates the format the component was written
under where it lands in the image, and a `.ts` with `export` in a directory read as CommonJS is a
syntax error there and not before.

## What a package ships is unchanged

Node does not erase types under `node_modules`. The components Toa and its extensions ship are read
from inside the installed package, so they are still transpiled into their `operations` directories
before they are published — nothing about them changes.

## Two files, one module name

A directory the bridge reads is a namespace, and the file name is the endpoint. `operations/do.js`
beside `operations/do.mjs` used to be read as one of them, chosen by whatever order the directory
came back in. It is refused now, and says which two it is:

```
Component at '/app/components/orders' has more than one operations/create: create.js and create.ts
```

It is raised for the directory, not for one endpoint, so it surfaces when the manifest is read
rather than when the endpoint is first called. No component in Toa or its extensions had one.

## An `operations` directory holds modules and nothing else

The components Toa ships were transpiled with declarations and source maps written beside their
code, and one of them carried a compiled unit test. Those directories now hold their modules and
nothing else. A component of Toa's is packed from the tree, so a package published from this
version ships less than it did and runs the same.

## What to do

1. Give a component written in TypeScript a `package.json` saying `"type": "module"`.
2. Rename one of any two files in one directory that resolve to the same name.
3. Write a relative import with the extension of the file that exists.
4. Write `import type` for a type.
5. Keep an `enum`, a `namespace` and a parameter property out of a component.
