# 1.0.0-alpha.253

## Identity token encryption

This release changes newly issued local identity tokens from PASETO V3.local to compact JWE using
direct symmetric encryption with AES-256-GCM (`alg: dir`, `enc: A256GCM`). It is a breaking
configuration change for every deployment that includes Exposition.

The `identity.tokens.keys` configuration changes from an object to an array. Each entry contains an
`id`, a secret `key`, and an optional `format` (`jwe` or `paseto`). The format defaults to `jwe`.
The first JWE entry is active for issuance; the remaining JWE entries are accepted for decryption.
Each `id` is written to the token as `kid`.

```yaml
# context.toa.yaml

configuration:
  identity.tokens:
    keys:
      - id: key0
        key: $IDENTITY_TOKENS_ENCRYPTION_KEY0
      - id: legacy0
        key: $IDENTITY_TOKENS_KEY0
        format: paseto
```

JWE keys must be base64url-encoded 256-bit secrets. Existing object entries are legacy PASETO
secrets: convert each one to an array entry with the same `id` and secret reference and add
`format: paseto`. Do not replace or remove them during this migration. The new runtime uses them
only to decrypt previously issued PASETO tokens, which are always marked for refresh.
The `format` discriminator is transitional: after PASETO support is removed, PASETO entries and the
property itself can be deleted while the `keys` array remains unchanged for JWE keys.

## Deployment procedure

1. Install the `1.0.0-alpha.253` CLI and generate a JWE key:

   ```shell
   toa key
   ```

2. Publish the generated value to the configuration secret in every target namespace before
   deploying the updated Context. Configuration secrets are not published by `toa deploy`.

   ```shell
   toa conceal configuration \
     IDENTITY_TOKENS_ENCRYPTION_KEY0=<generated-key> \
     --namespace <namespace>
   ```

3. Convert `identity.tokens.keys` to the array shown above in every Context and environment
   overlay. Add the new JWE entry first and convert all existing entries to `format: paseto`,
   preserving their IDs, secret references, and published values.

4. Confirm that the deployment now expects the new secret reference:

   ```shell
   toa export secrets <environment>
   ```

   The output must list the required key `IDENTITY_TOKENS_ENCRYPTION_KEY0` under
   `toa-configuration`.

5. Deploy the runtime and Context atomically. Do not serve traffic with old and new runtime
   replicas at the same time: old replicas cannot decrypt JWE tokens issued by new replicas.

6. Keep the legacy PASETO keys until the maximum lifetime of every token issued before the
   migration has elapsed. Removing them earlier forces affected clients to authenticate again.

## Rollback

The old runtime cannot read JWE tokens issued after the upgrade. Rolling back the runtime can
therefore interrupt authenticated sessions created or refreshed by `1.0.0-alpha.253`. If rollback
is unavoidable, expect those clients to authenticate again. Do not delete either the new JWE secret
or legacy PASETO secrets while rollback remains possible.

## Subsequent JWE key rotation

Deploy a new JWE key after the currently active JWE entry before activating it. In a subsequent
atomic deployment, move that entry before the previous JWE key; retain the previous key until every
token issued with it has expired. Any `format: paseto` entries may appear after the JWE entries and
do not participate in JWE issuance order.

```yaml
configuration:
  identity.tokens:
    keys:
      - id: key1
        key: $IDENTITY_TOKENS_ENCRYPTION_KEY1
      - id: key0
        key: $IDENTITY_TOKENS_ENCRYPTION_KEY0
      - id: legacy0
        key: $IDENTITY_TOKENS_KEY0
        format: paseto
```

See [Exposition token encryption and rotation](../extensions/exposition/documentation/components.md#token-encryption)
and the [`toa key` command](../runtime/cli/readme.md#key).
