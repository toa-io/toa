# Migrating from 1.0.0-alpha.285

The system properties of an entity are renamed. A database written by an earlier release is not
readable by this one.

**This release requires downtime**: the two versions must not serve at once. See
[The old and the new version must not run at once](#the-old-and-the-new-version-must-not-run-at-once).

## The names

| before     | after     |
| ---------- | --------- |
| `_version` | `VERSION` |
| `_created` | `CREATED` |
| `_updated` | `UPDATED` |
| `_deleted` | `DELETED` |

They are uppercase so that a system property is told apart from one of yours at a glance, wherever
a record is read — in an algorithm, in a criteria string, in a reply a client receives. `id` is
unchanged.

```javascript
export function transition (input, object) {
  return { created: object._created, version: object._version }
}
```

```javascript
export function transition (input, object) {
  return { created: object.CREATED, version: object.VERSION }
}
```

The new names are ordinary property names, so a manifest that still declares an old one is refused
where any misspelled property is:

```
/entity/schema/properties: pattern must match pattern "^[a-zA-Z]+([_a-zA-Z0-9]*[a-zA-Z0-9]+)?$"
```

## Where they are written

Everything that names a property of a record:

```yaml
entity:
  schema:
    properties:
      _created: { type: integer }

exposition:
  /:
    GET:
      io:output: [id, title, _created]
      query:
        sort: _created:desc
```

```yaml
entity:
  schema:
    properties:
      CREATED: { type: integer }

exposition:
  /:
    GET:
      io:output: [id, title, CREATED]
      query:
        sort: CREATED:desc
```

A criteria, a sort and a projection name properties, so they carry the new names too — in a
manifest, and in the query string a client sends:

```http
GET /pots/?criteria=_deleted=isnull=true&sort=_created:desc HTTP/1.1
```

```http
GET /pots/?criteria=DELETED=isnull=true&sort=CREATED:desc HTTP/1.1
```

A realtime route names the payload property it keys a stream by, and an event's payload is the
record, so a route keyed by one of these names it the new way.

## Existing data

The four are stored under their new names, so a record written by an earlier release is missing
every one of them as far as this one is concerned: it reads as never created, never updated, never
deleted and at version zero. Every index over them is over names nothing writes any more.

Rename them where they are stored, with a
[migration](/documentation/component/declaration.md#migrations) in every stored component of
yours. Every component this release ships carries the same one:

```yaml
# migrations/0001-system-properties.yaml
- update:
    filter: {}
    update:
      $rename:
        _version: VERSION
        _created: CREATED
        _updated: UPDATED
        _deleted: DELETED
```

`$rename` leaves a record that has none of the four alone, so it is a no-op against a database
this release wrote itself, and it is applied once, before the component serves. Migrations are
not inherited, so a component that takes a prototype writes its own.

Declare it before the migration that declares your indexes, so an index over one of the four is
built once, over records that already carry it. Such an index is rebuilt either way: the live one
is over a name nothing writes any more.

A component on a storage that does not apply migrations — anything but
`@toa.io/storages.mongodb` — has to rename the four itself, and declaring a migration against
such a storage stops it from starting.

## A page built on `svas`

`svas` merges a record by `_version` and removes it on `_deleted`. A page that uses `collection`,
`value` or `merge` needs the release of `svas` that reads the new names.

## The old and the new version must not run at once

**This release is not deployed by a rolling update.** Take the whole deployment down, then bring
this one up.

The first replica of this release to start renames the properties across the collection, and from
that moment a replica of the release before it is reading a database it does not understand. Two
things happen to it, and the first is silent:

- **Every deleted record reads as live.** It filters `_deleted: null`, and a missing field matches
  that, so every tombstone comes back — a deleted identity is a live one again, a revoked role is
  granted again.
- **Every transition fails.** Its compare-and-swap is on `_version`, which no record carries any
  more, so nothing matches, the operation retries and throws.

A rolling update runs both versions on purpose, which is exactly what must not happen here. Scale
the deployment to zero, or delete it, and only then apply this one. The gap is the migration:
seconds on a small collection, longer on a large one, and no replica serves until it is done.

Rolling back has the same shape in reverse: a database this release has migrated cannot be read
by the one before it. Going back means stopping everything and renaming the four the other way —
there is no migration that does it for you, so a backup taken before the upgrade is what a
rollback is built on.

## What to do

1. Rename the four properties wherever a record is read or written — an algorithm, an event, a
   receiver, a guard.
2. Rename them in every manifest: the entity `schema`, an `io:output` list, and a declared
   `criteria`, `sort` or `projection`. Indexes are declared in a migration — see [286](286.md).
3. Rename them in the query strings a client sends.
4. Regenerate types with `toa types`.
5. Take the `svas` release that reads the new names, if a page of yours uses it.
6. Write `migrations/0001-system-properties.yaml` for every stored component of yours.
7. Back the database up. A rollback has nothing else to stand on.
8. Stop every replica of the release before this one.
9. Deploy, then read `system_migrations` to see each one applied.
