# 1.0.0-alpha.262

This release adds the Introspection extension, which builds a map of an application: its components
as their manifests declare them, and the connections between them as they are actually used. The
extension is predefined, so it participates in every Context whether or not it is declared, and it
publishes a UI. Both are breaking changes for existing deployments.

## Introspection is added to every Context

Introspection ships two components, `introspection.nodes` and `introspection.edges`, and a service,
`introspection-explorer`, that hosts them. Because the extension is predefined, they appear in every
Context and bring two requirements with them:

- **a database.** Both components are stored, so the Context must define `mongodb`. Without it, the
  pointer for `introspection.nodes` cannot be resolved and `toa export` fails.
- **Exposition.** The components declare an `exposition` block so that the map is readable over
  HTTP, which makes Exposition a dependency of Introspection. A Context that does not annotate
  `exposition` fails with `Exposition context annotation is required`.

A Context that satisfies neither must turn Introspection off:

```yaml
# context.toa.yaml

introspection: false
```

## The UI requires an ingress

Introspection publishes its UI at `/.introspection` and therefore declares an ingress. Where that
ingress lands is the Context's business, and it is now declared in one place for every service:

```yaml
# context.toa.yaml

ingress:
  hosts:
    - api.example.com
  class: alb
  annotations:
    alb.ingress.kubernetes.io/group.name: example
```

Without this section `toa export` fails with `Service 'introspection-explorer' declares an ingress,
but no hosts are defined`. Add the section, or keep the map without publishing it:

```yaml
introspection:
  ui: false
```

`hosts` must list the same hostnames the Exposition `authorities` map to. Exposition continues to
derive its own hosts from `authorities` and to accept its own `class` and `annotations`; whatever a
service declares for itself wins, and the Context section fills in the rest. A UI published on a
hostname that Exposition does not serve cannot reach the map.

The UI itself is served without authentication — it is a page, and the data it displays is behind
the `system:introspection` role like every other resource. That role is granted by the holder of
`system` through `/identity/roles/:identity/`; nothing grants it automatically.

`/.introspection` is deliberately distinct from `/introspection`: the latter is where the map's own
components are exposed, as `/{namespace}/{name}` is for every component.

## An application that starts its own services starts one more

A cluster gets the explorer from the chart, but a setup that runs services itself — `toa serve
exposition`, `toa serve realtime` under pm2, Compose, or a shell — now has a third one:

```shell
$ toa serve introspection --env application/.env
```

It reports no readiness, unlike the gateway, so a process manager told to wait for one (pm2's
`wait_ready`) times out on it. Leave that off for this service.

Its variables come from the same environment file as everything else, and there are three new ones:
`TOA_INTROSPECTION`, which is global and is also what turns collection on inside every
composition, and the two database pointers of the map. Regenerate the file before starting anything:

```shell
$ toa env local -p application -d -i
```

Started without them, the service says so and exits — there is nothing for it to run. The same
absence silently disables collection in a composition, which is the intended way to turn the
extension off.

## The page in a local run

There is no ingress on a developer's machine, so the page is on the explorer's own port, and `/`
redirects to the mount path — <http://localhost:8002> is enough.

The page reads the map from its own origin, which is why `ingress.hosts` must list the hostnames
Exposition serves. On a local hostname it asks `:8000` instead, since the explorer and the gateway
are then two ports rather than one host. Neither case is configured; there is nothing to set.

## Service ports must be unique

A port may now be claimed by one service only, and `toa export` fails when two claim the same one:

```
Port 8000 is claimed by both 'exposition-gateway' and 'introspection-explorer'
```

In Kubernetes these are separate pods and would not have collided, but `toa mono` and a local run
put every service in one process. The reserved ports are `8000` for the Exposition gateway, `8001`
for the Telemetry readiness probe, and `8002` for the Introspection UI. An extension of your own
that runs a service must pick another.

## `boot.remote` takes a source

A call now carries the identity of its caller, so the callee can attribute it. Services declare
themselves through a new optional second argument:

```js
const remote = await boot.remote(locator, { service: 'my-service' })
```

The declared signature was `remote(locator)` and the manifest parameter was never part of it, so
TypeScript callers are unaffected. A JavaScript caller that relied on the undeclared second
parameter must move it:

```js
// before
await boot.remote(locator, manifest)

// after
await boot.remote(locator, undefined, manifest)
```

The rest of the contract change is additive and needs no action: `request.source` is a new optional
property, `Factory.emitter` receives the locator as a third argument, and an extension's
`components()` export receives the Context annotation.

### Anything that calls components should name itself

The source is what the map attributes a call to. A caller that omits it is recorded as a service
literally named `unknown`, and those calls pile up as an origin nobody can trace.

The runtime names its own entry points — `exposition`, `realtime`, `cli` for `toa call`, and
`features` for the integration stage. Do the same wherever your application reaches a component
outside a component: a maintenance script, a migration, a bespoke worker.

```js
const remote = await boot.remote(locator, { service: 'backfill' })
```

`@toa.io/userland/stage` now passes `{ service: 'features' }` on your behalf, so a test run no
longer leaves `unknown` behind. Runs from before this release did: the map is additive and keeps
what it collected, so drop the `introspection_edges` documents whose `src.service` is `unknown`
if you want them gone.

## A composition owns the process's discovery

`boot.composition` now depends on the process-wide lookup connector, so an unanswered lookup cannot
outlive the composition that triggered it. Before, a lookup for a component that never appears held
a connection open that nothing could close, and the process would not exit.

Nothing to do; extensions and applications are unaffected.

## `toa invoke` is removed

The command booted a single component in isolation and called one operation on it. Use `toa compose`
and `toa call` instead: the first runs the components, the second calls one of them.

```shell
$ toa compose ./components/orders
$ toa call orders.items.add "{ input: { sku: 'x' } }"
```

## Deployment procedure

1. Add the `ingress` section to every Context and environment overlay, listing the hostnames that
   Exposition already serves. Alternatively set `introspection: { ui: false }`, or `introspection:
   false` in a Context with no `mongodb` or no `exposition`.

2. Confirm the deployment describes what you expect before applying it:

   ```shell
   toa export deployment <environment>
   ```

   The output must contain the `introspection-explorer` service, and its ingress must carry the
   path `/.introspection` and port `8002`.

3. Deploy the runtime and Context. No ordering constraint applies: replicas of both versions can
   serve traffic at the same time. An old caller sends no `source`, and a new callee records such a
   call as originating from an unidentified service.

4. Start the explorer wherever services are started by hand, and regenerate the environment file
   first — see *An application that starts its own services starts one more*.

5. Grant `system:introspection` to whoever should read the map. Nothing else grants it, and
   without it the map answers `403`.

## Rollback

Collection is additive and lossy by design, so a rollback simply stops the map from being updated;
what was collected stays in the database. Removing the `ingress` section is only necessary if you
also roll back the Context — an older runtime ignores it.
